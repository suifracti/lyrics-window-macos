## 4. 用户旅程审计

### Journey 1：第一次打开 Lyric Island

| 维度 | 评估 |
|------|------|
| 用户目标 | 看到歌词 |
| 实际体验 | 如果 Spotify Desktop 已播放，App 自动连接并显示歌词。如果未播放，显示空白深色画布 + 顶部 hover 可见的橙色圆点（需要 hover 到顶部才能看见）|
| **问题** | 首次启动无任何引导。用户不知道需要 hover 到顶部边缘才能看到工具栏。空画布无任何提示文字或图标 |
| 严重程度 | **A** |
| 建议层级 | Level 1 需要一个轻量的空态占位（"等待 Spotify 播放…"或欢迎词） |

### Journey 2：Spotify 已播放，App 自动显示歌词

| 维度 | 评估 |
|------|------|
| 用户目标 | 安静看歌词跟唱 |
| 实际体验 | V3 沉浸模式运作良好。封面取色背景 + 当前行高亮 + 平滑滚动。工具栏隐藏 |
| **优点** | 非常符合"表面安静"原则。当前行明确是视觉中心 |
| 问题 | 当同时开启翻译 + 假名 Ruby + 罗马音时，每行歌词下方堆叠过多辅助层，非当前行信息量远超歌词本身 |
| 严重程度 | B |
| 建议 | 默认只显示原文 + 最多一种辅助层；多层需在设置中手动开启 |

### Journey 3：歌词已同步，用户只想安静听歌

| 维度 | 评估 |
|------|------|
| 用户目标 | 零干扰 |
| 实际体验 | V3 模式下完全满足。工具栏隐藏、进度条安静、歌词自动滚动 |
| **评价** | ✅ 这是 App 最佳场景，完全符合产品原则 |

### Journey 4：只有纯文本歌词，自动排轴在后台运行

| 维度 | 评估 |
|------|------|
| 用户目标 | 不需要理解什么是"排轴"，只想歌词能跟着走 |
| 实际体验 | systemV1 状态渲染器显示"待对齐时间轴"、工程术语密集的详情文字、以及"自动排轴"按钮 |
| **问题** | 面向用户暴露了"对齐时间轴"、"识别音频并与已知歌词逐行对齐"、"低置信/未匹配 N 行已标出"等工程概念。普通用户只需要知道"正在同步中…"即可 |
| 严重程度 | **A** |
| 建议层级 | Level 1 只需极简提示 "同步中…"；Level 3 展开后才显示置信度/行数等细节 |

### Journey 5：当前歌曲找不到歌词

| 维度 | 评估 |
|------|------|
| 用户目标 | 知道找不到，能手动处理 |
| 实际体验 | 显示 "未找到歌词" + "Local → LRCLIB → 网易云/QQ（实验）多别名查询中" |
| **问题** | "Local → LRCLIB → 网易云/QQ（实验）多别名查询中" 暴露了完整的 Provider 链条和查询策略，对普通用户毫无意义 |
| 严重程度 | **A** |
| 建议 | Level 1 只说 "未找到歌词"；Level 2 提供"手动搜索"按钮；Level 3 才显示来源细节 |

### Journey 6：用户手动搜索并选择候选

| 维度 | 评估 |
|------|------|
| 用户目标 | 找到正确歌词 |
| 实际体验 | SongSearchPopover 弹出，可输入歌名搜索，看到候选列表 |
| 问题 | 搜索入口需要先 hover 工具栏然后点击放大镜。首次使用的用户不知道这个入口的存在 |
| 严重程度 | B |

### Journey 7：用户开启翻译或读音

| 维度 | 评估 |
|------|------|
| 用户目标 | 看翻译/假名 |
| 实际体验 | 需要在 CurrentSongOperationsView 的"显示层"区域逐一 toggle。或者去设置中修改 |
| 问题 | CurrentSongOperationsView 是 360px 宽的 Popover，内容极深（歌词版本→版本状态→显示层→读音版本→翻译版本→自动排轴→排轴工作台），滚动量大 |
| 严重程度 | B |
| 建议 | "显示层"控制可作为 Level 2 直接附在歌词区域右键菜单或语境按钮中 |

### Journey 8：用户发现翻译有问题并进行修改

| 维度 | 评估 |
|------|------|
| 用户目标 | 修改翻译 |
| 实际体验 | 需要打开编辑器窗口（通过 CurrentSongOperationsView → "编辑当前版本" → 打开独立窗口）|
| 问题 | 路径长且需要切换窗口。但编辑器作为独立窗口是合理的，因为编辑操作需要足够空间 |
| 严重程度 | C（可接受） |

### Journey 9：用户查看或恢复旧版本

| 维度 | 评估 |
|------|------|
| 实际体验 | 需要通过 CurrentSongOperationsView → "查看版本历史" → 打开编辑器 |
| 问题 | 路径合理但较深 |
| 严重程度 | C |

### Journey 10：用户打开完整歌词工作台

| 维度 | 评估 |
|------|------|
| 实际体验 | CurrentSongOperationsView 是当前最接近"工作台"的入口，但它是一个 360px Popover，不是正式窗口 |
| **问题** | Popover 宽度有限，7 个功能区段（歌词/版本/显示层/读音/翻译/排轴/导入导出）全部纵向堆叠在内。"工作台"概念并未作为独立窗口或面板存在 |
| 严重程度 | **A** |
| 建议 | Phase 3 应将此 Popover 的内容整理为 Level 3 "歌曲工作台"面板，可以是 Sheet / Inspector / 独立窗口 |

### Journey 11-13：悬浮歌词、顶部胶囊、全屏

| 维度 | 评估 |
|------|------|
| 实际体验 | 三者均可正常工作。胶囊的 collapsed→hover→expanded 动画精致 |
| **问题** | 三种形态的视觉语言不完全统一。悬浮歌词有独立的材质设定（ultraTransparent / lightMaterial），胶囊是黑色灵动岛风格，全屏复用 V3 背景。它们看起来更像三个独立产品 |
| 严重程度 | B |

### Journey 14：用户修改 Settings

| 维度 | 评估 |
|------|------|
| 实际体验 | 9 个设置分类，NavigationSplitView 侧边栏 |
| **问题** | 设置项目数量庞大（AI 设置页超过 30 个控件，包含 Base URL、Temperature 等高度工程化的概念）。部分分类如"数据与存储"直接展示 SQLite Schema Version、Migration Version、LyricLine Count 等，完全是开发者诊断级别的信息 |
| 严重程度 | **A** |
| 建议 | 普通用户只需 Level 1-2 层级的设置（显示层、字号、悬浮窗开关）；API 配置、数据库诊断、Provider 排序等归入 Level 4 高级 |

### Journey 15：用户关闭高级功能，回到零操作默认状态

| 维度 | 评估 |
|------|------|
| 实际体验 | 没有"恢复默认"一键操作。用户需要逐项关闭翻译、假名、罗马音等 |
| 严重程度 | B |

## 5. 各窗口与模式审计

### 5.1 主窗口 V3 沉浸

- **优点**：封面取色背景美观、当前行高亮清晰、hover 工具栏保持画面干净
- **问题**：
  - 工具栏 6 个图标区分度低（均为灰白色 15pt SF Symbol，紧密排列）
  - Provider 状态菜单（绿/橙圆点）承载了过多功能（连接状态 + 歌词版本 + 翻译 + 排轴 + Mock Preview），是一个"万能菜单"
  - "当前歌曲操作"按钮和 Provider 状态菜单内容高度重叠

### 5.2 主窗口歌词专注（Legacy）

- 纯歌词滚动 + 底部播放控制条
- 视觉上与 V3 差异较大，更像早期开发版本
- 保留为 fallback 是合理的，但不应作为推荐

### 5.3 悬浮桌面歌词

- 功能正确：同步滚动、hover 控制栏、锁定/穿透/关闭
- **问题**：交互模式说明不足。"鼠标穿透"概念需要先理解才能使用

### 5.4 顶部胶囊

- **优点**：三态动画精致，信息密度控制得当
- **问题**：expanded 态右侧歌词区域较窄，多层歌词（翻译+假名）时容易溢出

### 5.5 全屏歌词

- **优点**：复用 V3 背景，视觉一致性较好
- **问题**：底部控制栏的 Slider 和 macOS 原生 Slider 不一致

### 5.6 编辑器窗口

- 功能完整：时间戳编辑、行操作、导入导出
- **问题**：工具栏按钮极多，且与主窗口的功能（翻译、读音、版本历史）存在重复入口

## 7. 默认层与 DIY 层的冲突

### 核心矛盾

产品原则要求"表面安静，里面很深"，但当前实现中：

1. **安静层泄漏了深层信息**：
   - Provider 状态菜单、歌词加载详情、排轴技术细节均在 Level 1 直接暴露
   - 设置界面没有区分"普通"和"高级"，所有 30+ 控件平铺

2. **深层入口分散且重复**：
   - 翻译操作同时存在于：Provider 状态菜单、CurrentSongOperationsView、编辑器
   - 歌词版本操作同时存在于：Provider 状态菜单、CurrentSongOperationsView、编辑器
   - 排轴操作同时存在于：Provider 状态菜单、歌词画布状态视图、CurrentSongOperationsView

3. **"歌曲工作台"概念未成型**：
   - CurrentSongOperationsView 是 360px Popover，内容量远超 Popover 合理承载
   - 编辑器是独立窗口，但只处理时间戳和文本编辑
   - 翻译、读音、版本管理散落在多个 surface

## 8. 已知问题验证

| # | 预设问题 | 验证结果 |
|---|---------|---------|
| 1 | 原文、Ruby、假名、罗马音是否重复显示 | ✅ **确认**。独立假名行模式 + 罗马音 + 翻译同时开启时，一行歌词下方堆叠 3 层辅助文字 |
| 2 | 辅助文字是否比原歌词更抢眼 | ⚠️ **部分确认**。辅助文字字号较小但数量多时，视觉重量可能超过原文 |
| 3 | 默认应只显示原文 + 最多一种辅助层 | ✅ **建议成立**。代码中默认 `showOriginal=true` 是对的，但翻译/假名/罗马音默认值取决于设置恢复 |
| 4 | 当前行是否真正成为视觉中心 | ✅ **是**。V3 的 emphasis 系统做得很好 |
| 5 | 播放器与歌词区域像两个拼在一起的产品 | ⚠️ **V3 模式下不成立**（融合良好）；Legacy 歌词专注模式下成立 |
| 6 | 工具栏入口过多、图标过密 | ✅ **确认**。6 个图标，且 #2 和 #3 功能重叠 |
| 7 | 为展示功能长期显示不必要按钮 | ✅ **V3 已解决**（hover 隐藏）；Legacy 模式下仍有此问题 |
| 8 | 大片无作用空白 | ❌ **不成立**。V3 的 responsive layout 处理得当 |
| 9 | 封面、背景和歌词照明是否属于同一视觉环境 | ✅ **V3 是**（封面取色背景）；全屏复用 V3 背景也是；悬浮窗和胶囊各自独立 |
| 10 | 搜索/来源/翻译/读音/排轴/版本散落多处 | ✅ **确认**。至少 3 个入口点 |
| 11 | 设置暴露过多内部实现 | ✅ **确认**。SQLite Schema Version、Migration v2 规划、Temperature、Base URL 等 |
| 12 | 自动排轴是否保持"后台自动" | ⚠️ **部分**。零操作开关存在，但状态 UI 暴露了太多技术细节 |

### 关键判断

> **主窗口是否真的需要同时承担播放器、歌词阅读、搜索、曲库和编辑器全部任务？**

**答案：不应该。**

- **编辑器**保持独立窗口
- **设置**保持独立窗口，但需重组信息层级

## 13. Phase 3.1 三套 Mockup 必须回答的问题

### 方案 A：安静优先
> 极致克制，默认体验接近 Dynamic Lyrics + Apple Music 混合体

- 默认画布只有歌词 + 封面 + 极简播放
- **必须回答**：高级能力的入口在哪里？如何从安静模式进入工作台？
- **矛盾**：如果太安静，用户可能永远发现不了翻译/假名/排轴等核心差异化能力

### 方案 B：工作台优先
> 明确的"安静/工作台"二元模式

- 默认安静模式 + 一个明确的"展开工作台"入口
- **必须回答**：工作台的形态是什么？Sheet? Inspector? Split? 独立窗口？
- **矛盾**：如何避免工作台变成设置仪表盘？如何保证工作台与安静模式的视觉连贯性？

### 方案 C：语境融合
> 没有明确的"模式切换"，但功能按语境自然出现

- 右键歌词行 → 显示翻译/假名/编辑
- 点击状态栏 → 展开排轴/来源细节
- **必须回答**：如何让用户知道"右键可以做更多"？发现性如何保证？
- **矛盾**：macOS 右键菜单的发现性天然弱；功能分散在多个语境中是否会让高级用户觉得效率低？

## 15. 审计结论

### 当前 Lyric Island 最严重的五个界面问题

1. **工程概念泄漏到默认界面**：Provider 链、排轴技术术语、SQLite Schema、Temperature 等面向开发者的信息直接出现在用户视野
2. **"歌曲工作台"概念缺失**：翻译、读音、版本、排轴、导入导出散布在 Popover + 菜单 + 编辑器三处，无统一收口
3. **首次启动空态**：黑色空画布无任何引导或提示
4. **Provider 状态万能菜单**：一个绿/橙圆点承载了连接状态 + 歌词版本 + 翻译 + 排轴全部操作
5. **设置信息层级平铺**：9 类 100+ 控件无区分普通/高级

### 默认界面中哪些内容必须删除、隐藏或延迟出现

- **删除**："Local → LRCLIB → 网易云/QQ（实验）多别名查询中" 等 Provider 链文案
- **隐藏**：排轴技术细节（置信度、行数、对齐策略）→ 降至 Level 3
- **延迟**：翻译引擎/候选/版本选择 → 需要时才展开
- **简化**："Mock Preview" → 普通用户不需要知道这个概念

### 哪些高级能力现在太难找到

- **显示层快捷切换**：需要进入 Popover 或设置
- **手动搜索**：需要先 hover 工具栏再点击
- **翻译操作**：隐藏在 Provider 菜单的二级项中

### 主窗口应该承担什么，不应该承担什么

- ✅ **应该**：歌词阅读 + 播放控制 + Level 2 语境操作
- ❌ **不应该**：编辑器功能 / 版本管理仪表盘 / AI 配置 / 数据库诊断

### 主窗口、桌面歌词、胶囊和全屏如何成为同一系统

- 共享相同的歌词渲染组件（LyricLineView ✅ 已做到）
- 共享相同的封面取色背景风格（V3+全屏 ✅ 已做到，悬浮窗 ❌ 未做到）
- 共享相同的空态/状态文案和图标
- 建立统一的"Lyric Island 视觉标记"（圆角、字体、颜色一致性）

### Phase 3.1 的三套设计方案分别必须探索什么矛盾

- **方案 A（安静优先）**：克制 vs 功能发现性
- **方案 B（工作台优先）**：模式切换 vs 视觉连贯性
- **方案 C（语境融合）**：右键菜单发现性 vs 高级用户效率

### 哪些现有体验必须保留为 Stable ID

见第 14 节完整列表。
