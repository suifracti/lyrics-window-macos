## 0. 不可丢失的原始项目基线

- **产品性质**：完全独立、可长期维护的原生 macOS 歌词应用，不破解或魔改 Dynamic Lyrics，不移植闭源 Lyricify。
- **技术栈**：SwiftUI 负责主要界面；AppKit 负责透明窗口、NSPanel、多窗口与点击穿透；SQLite 保存歌词、翻译、读音、排轴和历史版本。
- **首要播放来源**：Spotify Desktop 当前曲与播放控制；Spotify Web OAuth / PKCE 用于目录搜索与可靠身份。后续才评估 Apple Music 或系统媒体会话。
- **核心表面**：主窗口、全屏歌词、顶部胶囊、桌面悬浮歌词，以及后续菜单栏歌词。
- **歌词系统**：Provider 插件架构、本地优先、多源候选、可解释匹配、手动搜索、导入导出、锁定与历史版本。
- **AI**：OpenAI-compatible API、整首上下文翻译、Prompt 预设、个人风格、候选预览、人工编辑与永久保存；模型不能凭感觉猜时间轴。
- **自动排轴**：长期目标是在具备可靠音频与足够置信度时自动生成可用时间轴，不要求普通用户参与；复杂工作台同时提供音频来源、识别/对齐候选、置信度、Partial、人工打轴、偏移、修订、版本和恢复等完整 DIY 能力。自动结果不足时明确转为候选或请求人工确认，禁止模型猜时间轴。
- **固定浮动结构**：统一浮动系统、两个独立表面。顶部胶囊只负责紧凑状态、播放控制和最多一行当前歌词；桌面歌词负责自由位置、多行歌词、锁定和鼠标穿透。两者共享同一业务状态，但各自保留独立 WindowController 和窗口几何状态。
- **版本原则**：任何仍可维护的歌词、翻译、读音、排轴、Prompt、UI、布局、背景、材质、进度和动效都尽量保留稳定 ID，支持 current / recommended / classic / archived / experimental / designOnly；不静默覆盖旧版本。

## 1. 产品最终定位

### 一句话定位

> Lyric Island 是一款原生 macOS 歌词伴侣：平时安静地跟随 Spotify 展示歌词，需要时展开为能翻译、标注、编辑、排轴和保存个人版本的歌词工作台。

> **最高信息原则**：默认界面只显示用户完成当前任务真正需要的内容，不为了展示能力、解释系统或提高“可发现性”而堆入口、说明和工程状态。次要能力通过语境菜单、搜索、当前歌曲面板、Inspector 或高级页面在需要时被找到；**需要时找得到，不等于一直展示出来**。

### 双层产品结构

- **第一层：零操作歌词伴侣**：面向普通使用。打开 Spotify、播放歌曲，歌词应自动识别、自动获取、自动选择可靠版本、自动恢复用户偏好并自然出现；胶囊、桌面歌词、主窗口、全屏和菜单栏融入 macOS。默认路径的目标不是“少操作”，而是**在条件允许时不需要任何操作**。失败时再给出最少且清楚的下一步。
- **第二层：完全可 DIY 的歌词工作台**：面向多语言学习和深度用户。同一套自动能力都应允许按需展开和接管：来源、候选、匹配、翻译模型、Prompt、读音、显示层、排轴、置信度、人工修订、版本、导入导出与恢复均可细调。复杂模式不是普通模式失败后的简陋补丁，而是完整、透明、可控制的专业工作台。

> **自动与 DIY 并存原则**：Lyric Island 不在“简单”与“强大”之间二选一。默认层尽可能自动完成，普通用户无需理解内部过程；深度层允许用户接管每一步并 DIY 每项能力。半自动与人工流程只能作为自动能力尚未覆盖时的补全、校正和高级控制，不能替代“零操作自动完成”这一长期产品目标，也不能为了保持默认简洁而阉割工作台深度。

> **自动排轴开关的最终产品行为**：用户只需要在设置中开启一次“自动为未排轴歌词生成时间轴”。之后每首当前只有纯文本、没有可靠时间轴的歌曲，都由 Lyric Island 在后台自动完成捕获、识别、对齐、质量评估、保存与采用；普通用户不需要点击“边听边排轴”、进入编辑器、确认建议或手动补行。只有自动结果达不到安全阈值时，才保持原纯文本并给出非打扰式状态；完整 DIY 工作台作为用户主动展开的校正与接管层，不是默认必经流程。

- **自动链路**：检测到未排轴歌词 → 自动检查权限与音频可用性 → 自动选择识别/预处理路线 → 生成时间轴候选 → 质量门控 → 达标则保存为新版本并自动采用 → 主歌词立即按播放位置跟随；不达标则不伪造、不覆盖、不弹出强制操作。
- **开关语义**：开启后对后续每首未排轴歌曲持续生效；关闭后不再自动启动，但已保存的时间轴版本继续可用。可另设“仅 Wi‑Fi/插电时”“优先速度/优先准确”“允许下载本地模型”等高级选项。
- **安全边界**：自动结果必须可回退、可查看来源、可恢复原纯文本；不静默覆盖锁定版本；切歌取消旧任务；失败不污染当前歌曲。

### 核心价值

1. **自动获得歌词**：播放即识别，多 Provider 搜索、候选和本地兜底。
2. **真正理解歌词**：翻译、假名、罗马音、拼音、繁简、语境读音。
3. **保留自己的成果**：歌词、翻译、读音、排轴和 UI 都有版本、历史、锁定、归档与恢复。
4. **融入桌面**：同一数据投影到主窗口、全屏、桌面歌词、顶部胶囊和菜单栏。
5. **原生且克制**：不为了炫技持续占用 GPU，不把复杂能力做成网页后台。

### 明确不做

- 不取代 Spotify 成为完整音乐播放器。
- 不把产品改成 Electron、网页或 3D 播放器。
- 不照搬 Apple Music、Folia、Mineradio、Dynamic Lyrics 或 Lyricify。
- 不为了追竞品效果不断向主线塞功能。
- 不静默删除已做成且仍可维护的版本。
- 不让普通用户第一眼面对数据库、Provider、stable ID 或一整套工程参数。

### 18A-1 免费 UGC 歌词源研究候选

> 2026-08-04 Gemini 报告的可采纳结论：冷门日语、ACG、同人和 Vocaloid 歌曲的覆盖问题，更多是“现有免费正文源没有数据”，而不是检索引擎还不够复杂。中国平台的用户贡献歌词库可能包含已经制作好的 LRC/KRC/QRC/YRC，因此值得单独做来源覆盖审计；但报告中的覆盖星级、Dynamic Lyrics 具体实现、403 原因和所谓“黑科技秘密”都不是已经验证的项目事实。

- **优先研究对象**：现有网易云与 QQ 实验源的真实同步歌词覆盖；酷狗 Hash/KRC 仅作为待审计候选；必要时再评估其他免费 UGC 来源。
- **先做样本矩阵，不直接接入**：使用冷门日语、ACG/同人、Vocaloid、罗马音/英文别名、现场版和翻唱版样本，记录是否命中、行级/逐字时间轴、身份可靠度、地区限制、失败类型和重复候选。
- **进入 `experimentalFree` 的前提**：不付费；不依赖复制来的私有 Token、移动端密钥或 DRM；不使用来源不明的解密代码；明确缓存、导出、署名与发布风险；能被独立关闭和安全回退。
- **日本歌词站定位**：Uta-Net、UtaTime、PetitLyrics、Utaten、AWA 等在权利与接口未确认前只作为发现和浏览器外部打开入口，不自动提取、绕过 403、读取搜索引擎缓存或重新分发歌词正文。
- **不采纳“AI 搜索 Agent 抓缓存”方案**：搜索引擎缓存并不是稳定、完整或天然可再分发的歌词 API；AI 联网能力只用于发现页面、生成搜索词和解释下一步，不能绕过站点限制抓取歌词正文。
- **覆盖链路**：Local / SQLite → LRCLIB → 方案 B 中已启用的免费实验源 → 候选预览 → 外部发现 → 用户粘贴/导入 → 自动或人工排轴。上游有同步歌词时优先复用，但不能因此取消本地真实音频排轴与人工回退。
- **产品信息原则**：普通用户只看到“找到歌词、候选、导入、边听边排轴”等任务语言；来源枚举、Hash、格式解密、风险和诊断只在高级层按需展示。
- **18B 自动排轴重新验收**：技术链与验收 harness 已完成真实闭环：Spotify App 音频捕获、播放位置、不连续 Segment、临时 WAV、Speech、Partial DP、S3B 锚点、候选合并、编辑草稿、部分时间轴子版本、重启恢复、取消不写库、切歌防串歌和正式库隔离均已通过。产品层仍有一个明确缺口：默认 `appleMusicImmersiveV3` 不使用挂载 Assist Sheet 的旧 `LyricsCanvasView`，导致普通用户看不到或无法完成“边听边排轴”流程；顶部 S1/S2/S3A 调试菜单本来就只做诊断，不会让歌词自动跟播。下一步只修产品入口接线，不扩算法、不降低阈值、不进入 S3C。
- **编辑工作台**：原文、翻译、读音和行级时间必须明确分层；当前 Phase 2.11B 只收口行级时间轴，逐字时间保留为后续能力。任何保存都产生新版本，不直接覆盖已有或锁定版本。
- **Provider 失败与来源透明**：用户只需要知道候选来自哪里、是否有行级/逐字时间轴、为什么推荐以及能否安全采用，不显示内部堆栈、Hash、解密过程或工程枚举。高级诊断再显示来源分类、缓存/导出能力、地区限制和失败原因。

### H. 新发现的产品缺口

- **功能入口统一**：大量能力存在，但用户不知道从哪里开始。
- **完整用户旅程**：播放 → 获取 → 翻译 → 读音 → 修订 → 版本 → 下次恢复，需要一次走通。

- **默认模式硬验收**：当前行必须是唯一明确主角；默认最多展示原文与一种辅助信息；非当前行不完整展开假名、罗马音或翻译；不得同时出现两套等价罗马音；工具栏默认极简或按需出现；封面、背景、控制与歌词必须形成同一视觉空间；Wide、Small 与 Lyrics Focus 连续使用至少 20 分钟不显拥挤、空洞或疲劳。
- **学习模式与默认模式分离**：普通歌词伴侣默认只保留上一行／当前行／下一行及必要辅助层；假名、罗马音、翻译和读音学习信息只在学习模式或当前行按需展开，不因功能存在而常驻全部展示。
- **Mockup 比较方式**：三套高保真方案必须使用同一歌曲、同一窗口尺寸和同一信息内容，同时与当前版本及 Dynamic Lyrics 做并排对比；评审先看层级、克制、构图和阅读，再看风格辨识度与动效。不得复制 Dynamic Lyrics 的布局、素材或实现。
- 不是直接实现“潮汐”或任何单一概念。
- 制作三套同等完成度的高保真 Mockup。
- 每套必须包含播放中、暂停、Idle、加载、无歌词、错误。
- 每套必须覆盖 Wide、Small、Lyrics Focus，以及主窗口、全屏、桌面歌词和胶囊的关系。
- 用户确认方向后，才冻结色彩、字体、间距、材质、光效和动效原则。

### Phase 3.2：设计系统与组件库

- 在确认的方向上新增 Design Tokens、Surface Tokens 和 Motion Tokens。
- 统一按钮、菜单、卡片、状态、进度、版本标签和 Inspector。
- 旧 Token 保留；不为了组件化制造一层与业务无关的抽象。
- Preview Lab 用于 A/B 和多状态检查。

### Phase 3.3：Idle、连接、加载、错误与无歌词

- 解决未播放时空白问题。
- 分别设计 Spotify 未安装、未运行、未授权、已连接未播放、识别中、搜索中、失败、无结果和无歌词。
- Idle 可以使用最近播放、最近编辑或简洁引导，但不为填空白堆信息。
- 状态文案告诉用户发生了什么，以及下一步能做什么。

### Phase 3.4：主窗口重构

- 主窗口成为产品身份的核心表达。
- 保留现有响应式断点和歌词投影，只重构 Presentation。
- 处理封面、歌词、播放控制、当前歌曲入口、背景光效和窗口留白的关系。
- 新版本必须与经典主窗口并存，可随时恢复。

### Phase 3.5：当前歌曲与歌词工作流收口

- 让获取歌词、翻译、读音、编辑、排轴和版本管理成为连续流程。
- 不预先认定一定使用四个 Tab；先画流程，再选择 Inspector、Sheet、Popover 或分步操作。
- 普通用户只看到当前最相关且能立即执行的操作；其余能力按需展开或由用户主动寻找。不得为了证明功能丰富，把多个入口、解释文字、版本状态和工程选项同时铺在默认界面。
- 设置中心和当前歌曲入口继续共享同一 Store。

### Phase 3.6：设置中心与 Experience Library 重组

- 普通入口建议收敛为：常规、歌词与来源、翻译与读音、外观与体验、高级。
- 普通用户不显示 stable ID、designOnly、Debug signature、观察者数量、Provider 枚举或内部状态。即使进入高级页面，也先展示任务语言；工程元数据放在更深一层诊断入口。
- 高级用户仍能进入完整版本库、归档、实验和恢复。
- 经典设置中心继续保留恢复入口。

### Phase 3.7：全屏、桌面歌词、胶囊和菜单栏统一

- 共享设计语言，但根据表面角色保持差异。
- 胶囊是紧凑播放状态与一句歌词；桌面歌词是自由悬浮字幕；全屏是沉浸阅读；菜单栏是极轻量状态。
- 不重新创建 WindowController、PlaybackState、Session 或 Timer。
- 胶囊 v4 的顶部承载架构不推翻。

### Phase 3.8：歌词动效与视觉舞台

- 学习 Folia 的节奏感，不复制 Shader 或动画代码。
- 学习 Mineradio 的空间与光感，不引入重型 3D 渲染。
- 默认体验只使用低频、低幅、可关闭的动效。
- 不预先写死具体 spring、blur、opacity 和周期；以 Mockup、录屏和真实长时间使用为准。
- 更强的文字 PV、粒子或节拍效果只作为实验版本。

### Phase 3.9：性能、无障碍、多屏和长期使用

- Instruments 实测后再确定 CPU、内存和能耗目标，不把代理估算当事实。
- Reduce Motion、Reduce Transparency、Increase Contrast 和 VoiceOver 必须逐项验收。
- 多屏、无 notch、有 notch、不同刷新率和断开外屏都要验证。
- 长时间播放、快速切歌、网络恢复和窗口反复开关不能泄漏任务或观察者。

### Phase 3.10：真实数据、发布与最终精修

- 完成第 5 节的真实数据验收。
- 正式数据库备份、迁移、回滚和发布升级路径。
- 最终 Release 构建、签名、权限说明、截图、录屏和版本说明。
- 只在全部核心链路通过后，处理最后的像素、文字、动效和性能细节。

## 7. 视觉方向候选（尚未定稿）

> 目前不确认“潮汐”就是最终方向。下一轮必须把三套方案做成同等完整度的 Mockup，再决定默认推荐。任何代理不得在定调前创建 TidalThemeProvider、写死动画参数或把某套概念直接接进正式 UI。

### 方向 A：安静的深度／潮汐候选

- 关键词：安静、层次、封面色、柔和光源、深色空间。
- 优点：与“Island”和产品深度有自然联想，适合歌词长时间阅读。
- 风险：容易变成常见蓝紫 AI 渐变；持续呼吸或过度暗色会疲劳。
- 必须验证：明亮封面、暖色封面、黑白封面、白天长时间使用和 Reduce Transparency。

### 方向 B：歌词剧场

- 关键词：黑色幕布、聚光、歌词独白、极简控制。
- 优点：歌词焦点最强、性能风险低、适合全屏和专注模式。
- 风险：主窗口可能太空、封面和个人资产感偏弱。
- 必须验证：未播放状态、普通播放器信息、翻译与读音多层内容是否仍自然。

### 方向 C：个人歌词藏馆／唱片内页

- 关键词：封面、收藏、个人版本、内页、温暖材质。
- 优点：能表达“我的翻译、我的标注、我的版本”这一资产定位。
- 风险：可能偏复古或过重，和胶囊、菜单栏的现代感难统一。
- 必须验证：小窗口、桌面歌词、冷色封面和多语言信息密度。

### 补充候选：水墨／东方留白

- 关键词：留白、浓淡、旁注、印章感、中文与日文的自然排版。
- 优点：辨识度高，能让原文、翻译、假名、罗马音和拼音形成主文与旁注的层次；不依赖高功耗特效。
- 风险：风格化可能过强，西方流行音乐、明亮封面和小窗口中可能违和；竖排不能预设为默认。
- 当前归属：保留为视觉候选，不直接替换现有“个人歌词藏馆／唱片内页”方向。下一轮 Mockup 时可将两者分别做成候选，或先比较后选一个作为第三套正式命题。

### 定调方法

- 三套方案使用同一首歌、同一窗口尺寸和同一状态制作。
- 每套同时展示播放中、Idle、加载、无歌词、翻译/读音展开和当前歌曲操作。
- 不只看静态海报，必须看窗口缩放、切歌和连续播放录屏。
- 最终可以选择一套为 recommended，其余作为 classic / experimental，前提是确实可维护。

## 8. 完整用户旅程

### 8.1 正常播放

Spotify 播放 → Lyric Island 识别 TrackIdentity → 使用已锁定/当前歌词版本，或自动搜索 → 显示歌词 → 恢复用户已选择的翻译、读音、背景和窗口版本。

### 8.2 没有歌词

未命中 → 展示可理解的无结果状态 → 重新搜索/修改关键词/选择候选 → Provider fallback → 导入 LRC/TXT/粘贴/创建空白歌词 → 保存本地版本。

### 8.3 翻译

选择翻译 → 默认使用推荐引擎与 Prompt，也可展开高级参数 → 生成候选 → 校验行映射 → 预览 → 采用或编辑 → 保存新版本 → 可锁定、归档、切回旧翻译。

### 8.4 读音

检测语言 → 本地词典/语境引擎生成候选 → 标记不确定读音 → 用户确认或人工修改 → 保存为新版本 → 锁定后迟到结果不能覆盖。

### 8.5 排轴

可获得可靠同步时间轴 → 默认自动采用安全候选并恢复用户偏好；只有纯文本且没有时间轴时 → 系统在用户已授权的前提下可自动尝试边听边排轴，或按需使用本地完整音频 → 音频按 TrackIdentity、播放位置和连续区间暂存 → ASR 与行级强制对齐 → 高置信度结果可形成自动候选，低置信度/未解决行明确标记 → 深度用户可进入完整 DIY 工作台检查锚点、Partial、人工标记、偏移和版本 → 保存新时间轴版本并可恢复旧版本。默认路径追求零操作；半自动和人工是补全与接管层，不是最终默认目标。

### 8.6 快速切歌

A → B → C 时立即清除旧投影或进入加载占位；旧 Provider、翻译、读音、背景和排轴任务取消；任何迟到结果都不能写到新歌曲。

### 8.7 未播放与连接异常

- Spotify 未安装：解释依赖与可用的本地歌词模式。
- Spotify 未运行：提供打开 Spotify。
- 已连接未播放：安静 Idle 状态，不出现大面积无意义空白。
- 未授权：打开浏览器完成 OAuth 或说明自动化权限。
- 无网络：保留本地缓存和用户版本，说明在线能力暂不可用。

### 8.8 个人曲库与同步

用户编辑/采用的歌词资产进入本地个人曲库 → 可搜索、导出标准数据包、备份与恢复 → 用户主动开启私人同步后才跨设备同步。

### 8.9 多角色歌词

有角色数据时展示角色/和声；没有角色数据时回退普通歌词，不依赖模型自动编造角色。

## 9. 普通、学习与深度用户分层

### L1 普通用户

- 自动歌词、翻译开关、桌面歌词、胶囊和推荐外观。
- 只显示“重新搜索”“翻译”“显示读音”“编辑”这类任务语言。
- 不显示模型列表、Prompt、Provider 枚举、stable ID 和数据库字段。

### L2 多语言学习用户

- 目标语言、假名、罗马音、拼音、繁简、翻译风格和不确定读音确认。
- 能进入基础版本历史，但不必接触完整工程元数据。

### L3 深度用户

- Provider、候选评分、模型与 Prompt、个人词典、完整版本管理、排轴、导入导出、Experience Library 和实验功能。
- 高级能力必须是显式展开，不影响 L1 默认体验。

## 10. 本地参考项目的用途与边界

- **Dynamic Lyrics.app**：当前是默认歌词伴侣体验的直接质量基准。重点观察其原生 macOS 质感、当前行层级、信息克制、封面/背景/歌词整体构图、窗口行为和长时间使用舒适度；Phase 3 默认模式必须先达到并超过这些基础体验，再讨论 Folia 式视觉实验。只做黑盒观察，不逆向、不复制布局、素材或实现。
- **DynamicNotch（MIT）**：研究窗口定位和顶部锚定；可依法参考通用实现，但仍需独立设计。
- **boring.notch / Atoll（GPL）**：只研究状态层级、手势和连续形变思想，不复制源码。
- **Folia（AGPL）**：只研究文字节奏、视觉编排和空间氛围；代码、Shader、素材均不复制。
- **Mineradio（GPL）**：只研究光源、空间和音乐驱动反馈的概念；不引入 Three.js/3D 重型路线。
- **LyricsX（MPL）**：研究多播放器、桌面歌词、繁简和架构解耦；注意文件级许可证义务。
- **Lyricify**：研究歌词信息组织、多源候选和对唱表达；不以其 UI 为目标。
- **TaskbarLyrics（MIT）**：研究轻量表面、逐歌偏移和纯音乐回退。

### 参考过滤器

每次看到别人新效果，先回答：

1. 它服务什么真实用户任务？
2. 这个任务是否属于 Lyric Island 的核心？
3. 能否用符合原生 macOS、低功耗和许可证安全的方式重新设计？
4. 如果不是核心，是否只应进入实验室？

## 11. Codex、Fable／Antigravity 与模型分工

### 当前

- **当前执行状态**：Phase 2.11C-MVP1 已完全验收并冻结。真实 Spotify 自动触发、SCK 捕获、Whisper/S4 对齐、部分进度积累，以及受控完整结果的 `completeAndAdopt`、子版本保存与同步跟播均已获得真实证据。Grok 不再进入 MVP2、S4.6 或新的排轴研究阶段。下一主线进入 Phase 3.0–3.1：由 Antigravity / Gemini 负责只读产品与界面审计、用户旅程、信息架构及三套同等完成度的高保真 Mockup；Codex 继续负责架构保护、实现边界与后续集成验收。Phase 2.7、Phase 2.8 尚未开始，但不再阻塞 Phase 3。

### 功能阶段

- Codex 负责数据模型、SQLite、Provider、版本仓库、同步、排轴、窗口生命周期和合同测试。
- 大型数据阶段必须有独立 commit、临时数据库和受控启动；UI 小修不执行过重发布验收。

### Phase 3

- 高推理模型负责：产品审计、信息架构、用户旅程、三套视觉方向、设计系统与复杂交互决策。
- 快速模型负责：在已经确认的设计稿上改 SwiftUI、运行、截图、对照和小步迭代。
- 不允许代理跳过 Mockup 直接凭文字猜 UI。
- 每个表面独立分支/commit，先确认截图与录屏，再扩大范围。

### Antigravity／Gemini 的明确职责

> Antigravity 不是被取消，也不是因为不如 Codex。它是 Phase 3 的前端与视觉主执行环境；Codex 继续负责底层工程、架构保护、集成和验收。两者不是替代关系。

- **Gemini 高推理模型（Antigravity）**：负责 Phase 3.0–3.1 的界面审计、信息架构、完整用户旅程、三套同等完成度的高保真 Mockup、视觉方向比较和复杂交互方案。这个阶段先设计，不直接改 Swift。
- **Gemini 快速模型（Antigravity）**：在用户批准 Mockup 和设计规范后，负责 SwiftUI 前端实现、截图对照、窗口尺寸适配、视觉细节和高频小步迭代。
- **Codex**：继续负责 PlaybackState、LyricsSession、TrackIdentity、Provider、SQLite、迁移、同步、排轴、WindowController 生命周期、合同测试和最终集成；在 Phase 3 中重点审查 Gemini 的 UI 改动是否破坏共享状态、版本接口或数据安全。
- **协作顺序**：当前功能主线由 Grok 继续 Phase 2.11B；Antigravity / Gemini 并行负责 Phase 3.0–3.1 的只读审计与 Mockup，用户确认方向后才修改 SwiftUI；每个功能或表面完成后，再由 Codex 或独立审计检查共享状态、构建、数据库与回归。
- **边界**：Gemini 不得为了改 UI 复制第二套业务状态、Session、Timer、Provider 或数据库；Codex 也不再单独凭文字决定最终视觉。

## 12. 固定架构与版本规则

- 原生 SwiftUI + AppKit，不改成 Electron/Web。
- PlaybackState、LyricsSession、TrackIdentity、Provider、Timer、缓存和数据库不得因前端重构复制第二套。
- 所有表面使用同一只读播放/歌词投影。
- UI、布局、背景、材质、进度、动效、Prompt、翻译、读音和排轴的可维护版本都必须有 stable ID。
- 新版本不得静默覆盖旧版本；支持 current / recommended / classic / archived / experimental / designOnly。
- Preview 不写正式设置；Apply 才持久化；Cancel 恢复；未知 ID 安全回退但保留原值。
- “本次不使用”不等于删除；归档不删除；真正删除需要二次确认。
- 失败、危险、系统不兼容或维护价值过低的实现只保留截图、设计记录和 Git 历史。
- 正式数据库只能通过受控迁移流程打开；每次迁移先备份并验证回滚。

## 13. 验收效率规则

### 快速 UI 流程

设计/Mockup 确认 → 修改单一表面 → Debug build → 临时数据库/Mock 数据 → 截图或录屏 → 用户视觉验收 → 独立 commit。

不要求每次都做 Release、codesign、全量测试或正式数据库 SHA。

### 完整工程流程

只有涉及以下项目时使用完整验收：

- SQLite schema 或数据迁移。
- PlaybackState / LyricsSession / TrackIdentity。
- Provider、网络、OAuth、Keychain。
- WindowController、窗口生命周期和点击穿透。
- 同步、正式发布和升级路径。

### 证据必须匹配场景

- 单行↔多行必须真的发生换行。

## 14. Fable 报告的采用与修正

### 确认采用

- 产品不是功能简陋，而是能力不可见、工作流未收口、视觉身份未统一。
- 双层定位：歌词伴侣 + 歌词工作台。
- Phase 3 先审计和设计，再逐表面替换。
- #20 进入空间层次和灯光设计；#21 进入独立 Idle 状态。
- 普通/高级用户分层，旧 UI 保留版本。
- 动态桌面降级为实验。

### 暂不确认

- “潮汐”作为唯一最终方向。
- 五层背景、双光源、具体 blur/opacity/spring/周期等实现参数。
- 固定四 Tab 歌词工作台。
- 代理估算的文件数、代码行、内存、CPU 和开发天数作为项目事实。
- 用贬低 Folia/Mineradio 的方式证明 Lyric Island 有价值。

### 事实表达原则

- 仓库统计必须附可复现命令和时间点。
- 性能目标必须由 Instruments 与真实机器测量后冻结。
- 竞品功能、许可证和技术实现需单独核验。
- 产品价值来自选择不同深度，不来自宣称别人“里面是空的”。
